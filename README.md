# BookingTicketCinema-SDN-Assignment

## Add showtimes: manual or automatic suggestions
- Open **Quản lý suất chiếu → Thêm suất chiếu** (`/admin/showtimes`) and choose **Thêm thủ công** or **Đề xuất tự động**. Manual add/edit keeps the existing room selector and validation.
- Automatic mode takes movie, cinema, start/end dates, opening/closing times and ticket price. It has no room selector. The server chooses valid Active rooms with usable seats in the selected cinema, finds the earliest available gaps and balances equal-time choices between rooms. Existing schedules and their 15-minute cleanup intervals are checked, including legacy name-only room references.
- The preview is one chronological sequence for the selected movie, separated by movie duration plus 15 minutes; it does not fill all rooms with simultaneous screenings. Each film must finish by that day's closing time. Dates/times use Vietnam time (UTC+07:00); past times and dates before the movie's release are rejected/skipped as applicable. Limits: 31 inclusive days and 200 proposed showtimes.
- Example: a 120-minute movie, 09:00–23:00, three free days produces 18 suggestions (6/day). The preview groups slots by date and shows start/end times and the automatically chosen room on every slot. No showtime is created until the Admin reviews and confirms the preview. Changing any input clears the old preview and confirmation.
- `POST /api/showtimes/suggestions` accepts `{ movie, cinema, startDate, endDate, openingTime, closingTime, price }` and returns the preview plus a signed token valid for 15 minutes. `POST /api/showtimes/suggestions/confirm` accepts only `{ token }`. Both require an active Admin and the existing JSON/Origin write checks. The token belongs to the creating Admin and becomes invalid if the API server restarts.
- Confirmation rechecks movie/room versions, current room layouts, future times, release/classification and conflicts under the shared schedule guard. It saves the entire reviewed batch in a MongoDB transaction or saves nothing; it never silently substitutes another plan after a conflict. MongoDB must support transactions (replica set), as with the existing payment workflow. On an expired/stale preview, generate and review another proposal.
- Check with `npm run test:showtime-suggestions -w backend`, the existing showtime/room tests, and `npm run build`. The integration test writes only to a unique temporary database. For the complete backend suite, configure a test JWT secret and `NODE_ENV=test`, `ENABLE_PAYMENT_SIMULATION=true`, and a transaction-capable test MongoDB URI.

## UC-14 / UC-14.1: Cinema rooms and seat configuration

- Creating a room permits only Active (**Hoạt động**) or Inactive (**Chưa hoạt động**), defaulting to Inactive; the API enforces the same restriction. Maintenance remains available when editing an existing room.
- Applying a seat type or operational condition clears that selection. Select seats again for the next operation; previously edited groups are not implicitly included in subsequent changes.
- Admin opens **Quản lý phòng chiếu** in the account/Admin navigation, or `/admin/rooms`. Search by room name, filter by cinema/status, add/edit a room, change its status, or confirm deletion in the inline panel. New rooms default to Inactive and require a valid initial Rows × Columns layout. Capacity is derived from `seats.length`.
- Choose **Cấu hình ghế** to open `/admin/rooms/:id/seats`. Select individual seats, a row or all seats using native buttons (Space/Enter supported); apply Standard/VIP and Active/Broken/Maintenance/Disabled independently. Add/remove/rename positions or generate a replacement draft (1–26 rows, 1–40 columns, at most 1000 seats). Changes stay local until **Xem lại thay đổi → Xác nhận và lưu**. Review shows additions, removals, type/condition changes and current protected-reference conflicts. Cancel never writes. Save revalidates references and the room version; stale/conflicting writes return 409 and can be reloaded explicitly.
- Schema keeps `CinemaRoom.seats: [String]` and adds a Mongoose Map `seatConfigs[seat] = { type, status }`, enum validation and `lastModifiedBy` audit attribution. Metadata cannot reference absent seats. Existing rooms without metadata read as Standard/Active; no bulk migration or replacement of existing showtimes/bookings is performed. The import script accepts optional metadata and still preserves existing rooms. Cinema/name uniqueness remains case-insensitive within each cinema.
- **Application policy:** seat layouts and metadata are copied into newly created showtimes as `seats[].type` and `seats[].condition`. Booking state remains `available|held|booked`. Existing showtime snapshots and accepted prices never change when room metadata is saved; legacy snapshots default to Standard/Active. To change an already-created showtime, use its existing controlled editing/cancellation rules rather than retroactively disabling a purchased seat. The room editor displays this policy before editing and during review.
- For not-yet-ended showtimes (movie duration plus 15-minute buffer), affected held/booked seats and seats in active pending/paid bookings block unsafe removal, renaming, type or condition changes. Checks include `roomId` and legacy cinema/room strings. Missing duration is treated conservatively. Room renaming is blocked once any showtime references it; a room with upcoming/in-progress showtimes cannot become Inactive/Maintenance. Physical deletion is blocked by any showtime reference, including historical records. No automatic cancellation or refund occurs.
- Only Active operational seats can be claimed. The backend's atomic seat-claim query checks the showtime's operational snapshot, and Member/counter booking screens and public availability counts use the same condition. VIP has **no added price**: all seats retain the showtime's configured ticket price. Safe future changes leave paid booking amounts, holds and current snapshots unchanged.
- APIs (all require an active Admin): `GET /api/rooms?search=&cinema=&status=&page=1&limit=20`, `GET /api/rooms/:id`, `POST /api/rooms`, `PUT /api/rooms/:id`, `DELETE /api/rooms/:id`, `GET /api/rooms/:id/seats`, `POST /api/rooms/:id/seats/preview`, `PUT /api/rooms/:id/seats`. Create takes `{cinema,name,status?,seats,seatConfigs?}`. Update metadata takes `{cinema,name,status,version}`; delete takes `{version}`. Preview/save take `{seats,seatConfigs,version}`, with `confirmed:true` required on save. The detail response provides `version`, derived `capacity`, metadata and policy. Writes reuse existing JSON/Origin protections and log the acting Admin; responses contain no booking/User PII.
- The existing single-Node schedule write guard is shared by room writes, scheduling and booking creation so a local seat claim cannot interleave with the protection check/save. Conditional room versions additionally prevent lost Admin updates. This retains the current application's single-process deployment assumption; multiple independent API workers require a shared database lock/transaction protocol before scaling. Booking/payment transactions still require the repository's existing MongoDB replica-set setup; room CRUD itself works on standalone MongoDB.
- Tests: `npm run test:rooms -w backend` (HTTP/Mongoose + real holds/cash settlement), `npm run test:rooms:e2e -w backend` (real login, APIs, MongoDB, bulk editing, Cancel, Review, conflict after preview, desktop/tablet/mobile), `npm test -w backend`, `npm run build`. Browser tests use the existing Playwright dependency and `E2E_BROWSER_CHANNEL=chrome` or `msedge`; screenshots are in `.local/qa/rooms`. Tests create and remove only their unique temporary databases.
- Local Windows test setup: set `MONGOD_BINARY` to the installed `mongod.exe` when it is not on PATH, then run `npm run db:local -w backend`. In the test shell set `MONGODB_URI=mongodb://127.0.0.1:27019/booking_cinema?replicaSet=cinemaLocal` and `NODE_ENV=test`. The full existing suite also needs `ENABLE_PAYMENT_SIMULATION=true` for its explicit payment-simulation tests; this flag is not used by room management and must not be enabled in production. The task does not repoint or modify your existing `.env` database.
- Implemented using the existing React/Express/Mongoose MVC structure and `SDN302_AI_Coding_Rules.md`, with no new packages. `ui-ux-pro-max` guidance was applied to native selection controls, accessible labels/pressed states, keyboard focus, derived selection state and responsive layout while reusing `movies.css`. UC-14/14.1 text was checked against the linked requirements document; image-only diagrams were not independently verified.

Changed files: backend room route/controller/service, `CinemaRoom`/`Showtime` models, showtime/booking services, app routes, room import, package test scripts and `test_rooms.js`/`scripts/test-rooms-e2e.js`; frontend `ManageRooms.jsx`, `ConfigureSeats.jsx`, `SeatLayoutEditor.jsx`, `rooms.css`, room service, routes/Admin navigation, scheduling room refresh, booking seat controls and public availability helper.

## UC-19: Forgot Password backend

- Follows `SDN302_AI_Coding_Rules.md` and the UC-19, BR-1, BR-7 and BR-11 text in the linked requirements document. Activity/Sequence/Communication diagrams embedded as images have not been independently verified.
- Public endpoints: `POST /api/auth/forgot-password` with `{ email }`; `GET /api/auth/reset-password/verify?token=...`; `POST /api/auth/reset-password` with `{ token, newPassword, confirmPassword }`. Only Active/active Members are eligible. Pending, inactive, banned and staff accounts receive the same generic request acknowledgement as unknown emails. Password validation matches the current policy: at least 6 characters, non-blank, at most 72 UTF-8 bytes; confirmation must match exactly.
- A 32-byte random token is sent only by email. User stores `passwordResetTokenHash` (SHA-256), `passwordResetExpiresAt`, `passwordResetUsedAt`, `passwordResetRequestedAt`, and the issuing `passwordResetTokenVersion`, all excluded from normal queries. Successful reset sets the bcrypt hash and consumes the token in one conditional document update; concurrent/replayed/expired links cannot succeed. No MongoDB replica set or multi-document transaction is needed. A newer request replaces the previous link; ordinary password changes also invalidate outstanding links through `tokenVersion`.
- **Additional technical decisions, not confirmed UC-19 business rules:** default expiry is **30 minutes**, configurable with `PASSWORD_RESET_TTL_MINUTES` (positive whole minutes). Reset increments `tokenVersion` to revoke existing JWTs, does not automatically sign in, and preserves existing BR-7 lockouts. It does not modify role, profile, points or bookings.
- Configure `backend/.env` from `.env.example`: `MONGODB_URI`, `CLIENT_URL` (the frontend HTTP(S) origin), `PASSWORD_RESET_TTL_MINUTES`, `EMAIL_FROM`, `SMTP_HOST`, `SMTP_PORT`, `SMTP_SECURE`, `SMTP_USER`, `SMTP_PASS`. Existing Gmail aliases `GMAIL_USER` / `GMAIL_APP_PASS` take precedence; use a Gmail App Password, never commit credentials. Recovery requires configured real SMTP and never falls back to Ethereal, JSON transport, a returned token, or a logged reset URL. The link is `${CLIENT_URL origin}/reset-password?token=...`.
- Request responses do not wait for SMTP and never report delivery/account details. Delivery failures log only a fixed diagnostic code and revoke the matching undelivered token. Sending runs in-process; restart/crash can interrupt delivery, and users can request another link after the cooldown. This is not a durable delivery queue.
- Limits: 10 forgot requests per socket IP per 15 minutes; 60 verify/reset requests combined per IP per 15 minutes; at most one new link per eligible account per 60 seconds. IP limits return `429` with `Retry-After`, independent of account existence. Counters are memory-bounded and local to one Node process; multi-instance hosting needs a shared limiter store. Express does not trust `X-Forwarded-For` by default; only configure specific trusted proxies if deployed behind one. Exclude reset-token query strings and request bodies from reverse-proxy/APM logs. Recovery responses use `Cache-Control: no-store` and `Referrer-Policy: no-referrer`.
- **Postman:** start MongoDB and `npm run dev:backend`; POST `/api/auth/forgot-password` using an Active Member email, then copy the token from its delivered email (the API never returns it). GET `/api/auth/reset-password/verify?token=...` should return `{ success: true, valid: true }`. POST `/api/auth/reset-password` with that token and matching new passwords should return success; repeating it or verifying the used token returns `400`. POST `/api/auth/login` with the new password should work; the old password and old JWT must fail. An existing BR-7 lock must expire before login. Unknown/ineligible emails receive the same `200` request message.
- `npm run test:password-reset -w backend` runs HTTP integration checks against a uniquely named temporary MongoDB database and a real local TCP SMTP receiver. Success paths use real MongoDB, bcrypt and Nodemailer; targeted failure tests inject DB/hash failures. Test databases are removed after each run; tests never send mail to real Members. `npm test -w backend` includes these checks.
- Frontend recovery services now call these three endpoints using the existing Axios client. Invalid/expired/used links return the code `RESET_LINK_INVALID`, so the UI offers a new link; network, rate-limit and server failures remain retryable errors. Success states require an explicit successful backend response.

## UC-16.1 / UC-16.2: Revenue dashboard and CSV report
- Based on `docs/RDS-SWD391-Assignment.docx` (UC-16, UC-16.1, UC-16.2; BR-11, BR-13, BR-14) and `SDN302_AI_Coding_Rules.md`.
- Sign in as Admin, choose **Thống kê doanh thu** or open `/admin/revenue`. Filter an inclusive date range (up to 366 days), source, payment method, and daily/monthly grouping. Empty periods show zeros; failed calculations show an error without partial totals.
- Confirmed reporting convention: CSV with UTF-8 BOM for Excel, VND, `Asia/Ho_Chi_Minh` (UTC+07:00). Payments belong to their confirmation date and refunds to their completion date. `payments = gross - discounts + fees - points`; `net = payments - refunds`. `points` is the redeemed VND value, not the number of points, and is not counted as cash. Fees are included in money collected. A refund-only period may have negative net revenue.
- **Current source coverage:** finalized `FoodSale` cash receipts with confirmation, matching line totals and received cash/change are included. Pending, cancelled, reconciliation, and unconfirmed sales are excluded. Ticket revenue (including food bundled with a ticket) comes only from trusted `RevenueEntry` settlement/refund records. Existing `Booking.status = paid`, `paymentStatus = paid`, browser returns and mock payments are not proof and are never automatically converted into receipts. No historical ticket revenue or refunds are guessed from current catalogue prices or mutable booking timestamps.
- The current ticket payment/refund modules do not yet produce verified entries. Their producer integration remains required when those settlement UCs are implemented; existing demo ticket bookings therefore do not appear as verified ticket revenue. The dashboard and CSV both disclose this source limitation.
- `RevenueEntry` is an append-only reporting contract with **no public write endpoint**. Trusted ticket finalization must write a record in the same transaction as settlement, once per booking: `booking`, globally unique `reference`, `kind: payment`, `confirmedAt`, `currency: VND`, `method`, `evidence`, and integer `gross`, `discounts`, `fees`, `points`, `amount`. Cash uses `employee-receipt`, gateways use `provider-confirmation`, and zero-cash points-only settlements use `points-ledger`. Store the accepted price snapshot, never current movie/food prices. Only finalized evidence may enter this collection.
- A verified full refund creates a separate `kind: refund` entry for the original `booking`, method and entire cash `amount`, with `originalReference` pointing to its payment and the refund's actual confirmation date/evidence. Do not modify/remove the original payment. Unique booking/kind and reference indexes prevent duplicate final records; unconfirmed/failed refunds create no entry. Reporting rejects mismatched originals, partial cash refunds and invalid amount breakdowns.
- `POST /api/revenue/reports` takes `{ from, to, source, method, groupBy }` and returns a server-owned snapshot. `source`: `all|tickets|food`; `method`: `all|cash|vnpay|momo|credit-card|points`; `groupBy`: `day|month`. Both dates are `YYYY-MM-DD`. Confirmed entries and arrival timestamps are bounded by `dataTimestamp`.
- `POST /api/revenue/reports/:id/export` takes the same filters and returns a complete CSV from that stored result, without recalculating transactions. Only the creating Admin can export it; changed filters require refreshing, and snapshots expire after 30 minutes. CSV includes filters, timezone, data/export timestamps, basis, source coverage, totals, source breakdown and each period. All endpoints verify active Admin sessions; JSON/Origin checks protect requests, responses use `no-store`, and report creation/export log acting Admin and report IDs.
- Uses existing Express/Mongoose/React and a native SVG chart with a visible data table; no additional packages. New files: revenue route/controller/service, `RevenueEntry` and `RevenueReport` models, Admin page/CSS, frontend service, and `backend/test_revenue.js`.
- Checks: `npm run test:revenue -w backend`, `npm test -w backend`, `npm run build`. Integration tests create/remove their own unique temporary database and leave cinema data unchanged.

## UC-7.2 QR tickets and UC-10/10.1 Check-in (NhaNTK)
- Members open **Xem vé QR** from `/bookings`, or follow the link after payment, to `/bookings/:id/tickets`. Only the authenticated owner can read that order's QR codes. Each paid seat has its own random reference and downloadable QR PNG; no personal data is encoded. Used, revoked or expired tickets do not display usable QR codes.
- Tickets and their showtime snapshot are embedded in `Booking` at successful payment finalization. UC7.2 only reads already-issued tickets: opening or refreshing the page never creates tickets, changes references or writes booking/check-in metadata. A paid order without issued tickets displays its status and directs the Member to staff. Older existing code-only tickets retain their code and QR; missing display metadata is derived without writing. Reading/scanning a QR never checks it in.
- The QR page refreshes visible data every 15 seconds, on browser focus and when the tab becomes visible; manual refresh remains available. A failed refresh clears the previously displayed QR. Pending, cancelled, refund-requested, refunded and unverified bookings display their current result without usable QR. Refund states are integration-ready; UC7.1 execution is still separate.
- Employees open `/employee/check-in`, choose the showtime being admitted, and enter a reference, select a QR image (PNG/JPEG/WebP up to 8 MB), or explicitly enable their camera. Camera streams stop on exit; stale image results are discarded after changing showtime, disabling the scanner or leaving the page. Lookup is read-only and displays film classification, seat, current status and the admission window. K/T13/T16/T18 or an age-restricted legacy film requires the Employee to confirm physical age/guardian checks.
- `GET /api/bookings/:id/tickets` is Member-only. `GET /api/tickets/showtimes`, `GET /api/tickets/lookup?reference=...&showtimeId=...`, and `POST /api/tickets/:reference/check-in` are Employee-only. POST JSON is `{ showtimeId, ageVerified }`; employee identity always comes from the session. JSON/Origin checks protect writes, and ticket responses use `Cache-Control: no-store`.
- Admission defaults to **30 minutes before through 15 minutes after** the showtime. Optional `CHECKIN_OPEN_MINUTES` and `CHECKIN_CLOSE_MINUTES` configure these bounds (whole minutes, 0–180). The existing agreed database, ports and payment-return configuration are unchanged.
- Verified admission requires a matching trusted `RevenueEntry` payment (reference, VND amount, method, evidence and original hold deadline), no confirmed refund, valid booked-seat ownership, and a valid window. A single conditional Booking update rechecks Paid/payment reference, method and amount, the showtime/age snapshot, selected seat and unused ticket. MongoDB checks the admission deadline at write time; the same update stores check-in time and the acting Employee. Concurrent/replayed requests cannot admit the same ticket twice; different seats may check in independently. Existing code-only ticket metadata is added only with successful check-in, preserving codes and QR images.
- UC10 calls UC10.1 through the same confirmation action. The UI stops confirmation after its displayed window expires. An uncertain write returns no admission claim; the page rereads the live ticket, shows the uncertainty and requires a new lookup before another confirmation. A reread showing Checked-in never turns the failed request into a success message.
- Cash, verified VNPay IPN and zero-amount settlements produce trusted payment evidence and verified tickets. Demo tickets remain explicitly marked and do not grant real admission or revenue. VNPay live/Sandbox provider validation still requires merchant configuration and a real provider test.
- Future refund finalization must update the same Booking status conditionally against unused tickets as part of its trusted settlement transaction; a pending refund must leave Paid before any check-in can succeed. No refund execution or payment-gateway integration is added by these UCs.
- `npm run test:tickets -w backend` creates/removes an isolated temporary database and tests ownership, read-only QR views, missing issued tickets, receipt validation, parallel check-in, time/age rules, cancellation/refund and seat changes, demo isolation, unsafe requests and uncertain storage outcomes. `npm test -w backend` runs all regressions; `npm run build` builds the frontend. QR generation uses `qrcode`; camera/image reading uses a lazy-loaded `@zxing/browser` module.

## Run backend
Run these commands from the repository root after installing Node.js and MongoDB Community Server:

```sh
npm ci
npm run setup:local
npm run dev:backend
```

`setup:local` starts the single-node `cinemaLocal` replica set on port 27019. It finds `mongod` on PATH or in the normal Windows MongoDB Server installation folder; use `MONGOD_BINARY` in your private `.env` for another installation location. No manual Windows service reconfiguration or extra npm package is required.

If `backend/.env` already points to local MongoDB on port 27017, **stop the backend before setup**. Setup backs up `.env` and the original database to `.local/backups`, copies collections with their indexes and BSON types, verifies content checksums, and only then updates `.env`. The database on 27017 is not modified. Different existing target data is never overwritten. This importer supports ordinary collections, up to 50 MB total and 50,000 documents per collection; use MongoDB Database Tools for larger/other databases. Remote/Atlas URIs are not rewritten.

For a fresh clone with no `.env`, setup creates it from `.env.example` with random local JWT/cookie secrets. **Only for a new empty demo database**, run `npm run seed -w backend` once. Do not seed a database you want to preserve: the existing seed script resets demo collections.

On subsequent runs (including after reboot), run `npm run setup:local` before starting the backend; it reuses the replica set and existing configured data. `.env`, `.env.setup-tmp`, `.local` database files and private backups are ignored by Git. Commit source code, scripts and `.env.example`, never local data or credentials.

Payment supports verified cash and zero-amount settlement, with optional VNPay Sandbox integration and explicitly labelled development simulation. See [payment setup](docs/PAYMENT_SETUP.md) and the UC9.3 contract above for configuration and reconciliation.

### UC-15: F&B and promotion configuration

- In the Admin dashboard, choose **Quản lý F&B** or **Quản lý khuyến mãi**. Both lists support Add, details, Edit, Cancel, confirmed Delete, empty states and retry after retrieval failures.
- F&B fields: name, description, image URL/local path, whole-VND price, integer stock and availability. Active names must be unique, ignoring case. Legacy items without stock can be edited to establish their starting inventory.
- Open counter orders (pending, payment received or reconciliation) and unexpired pending ticket orders protect products from deletion. Such products cannot change price/availability or reduce stock; replenishment and descriptive edits are allowed. Completed counter receipts retain their original item names and prices.
- Promotion fields: unique uppercase code, name/description, percentage (1–100) or fixed VND discount, minimum order value, optional percentage discount cap, scope (food/ticket/all), explicit stacking choice, start/end, optional total usage limit and activation flag. Empty usage limit/cap means unlimited. Codes remain reserved after deletion for historical traceability.
- Start/end fields are entered/displayed in Vietnam time (UTC+7), sent with an explicit offset and stored as UTC. End must be after start. Admin can manage past/future campaigns; the public eligibility list excludes paused, future, expired, exhausted and deleted records.
- `usedCount` is server-owned and cannot be changed through Admin requests. A usage limit cannot be lowered below usage already recorded. After use, code, discount type/value and scope are locked. Creates/updates/deletes record the acting Admin; failed or cancelled requests do not change financial history.
- API for each resource (`foods` or `promotions`): protected `GET /api/<resource>/admin`, `GET /api/<resource>/admin/:id`, `POST /api/<resource>`, `PUT /api/<resource>/:id`, `DELETE /api/<resource>/:id`. Update/Delete require the loaded `version` (`__v`). Writes require JSON and reject cross-site/untrusted-origin requests.

These endpoints configure/expose campaign rules; they do not apply or redeem a discount.

Existing point payments and the cash-only F&B screen do not automatically apply promotion codes in this change.

### UC-11: Standalone food and drink sales
- Sign in as an Employee, then open **Bán đồ ăn & thức uống** at `/employee/food-sales`.
- Select quantities, request the server-generated quote, confirm the total with the customer, enter the cash received and confirm receipt. The final receipt retains the item names, unit prices, quantities, total, employee, payment time and change.
- Only cash is implemented. This flow creates no booking, seat hold or movie ticket. VNPay, promotions, membership points and revenue dashboard integration are separate work.
- The `Food.stock` field is a non-negative integer. Existing products without stock cannot be sold at this counter until inventory is set. Optional local demo: `npm run seed:food-counter -w backend` adds three products with 30 units each **only if their names do not already exist**; it does not clear data or replenish existing items.
- API base `/api/food-sales`: Employee-only `GET /catalogue`, `POST /` (items and `requestId`), `GET /:id`, `POST /:id/cancel`, `POST /:id/pay`. An Employee can only access their own orders.
- Creating a quote snapshots server prices without deducting stock. Cancelling is allowed before cash confirmation. Request IDs and paid-order retries prevent duplicate orders or duplicate stock deductions.
- Finalization runs in a MongoDB transaction, so stock and the Paid receipt commit together. Cash receipt evidence is persisted first. If price/stock changed or finalization fails, the payment stays traceable for staff reconciliation; never collect cash again for that order. Reconciliation/refund resolution requires the cinema's operating procedure; there is no automatic second charge or manual Paid override in this screen.
- An order ID is retained in the browser session for refresh/recovery. If the response is lost, reopen the order and retry finalization of the existing payment, rather than creating a new payment.

#### MongoDB requirement for counter payment

Transactions need a replica set (a single-node replica set is sufficient locally). The agreed database and application ports remain `booking_cinema`, backend 3000 and frontend 5173. On standalone MongoDB, the UI disables payment and the API returns 503 before recording cash; quoting and cancellation still work.

To enable transactions on the local MongoDB service, add this top-level configuration to its `mongod.cfg`, restart the MongoDB service, then initialize the replica set once from `mongosh`:

```yaml
replication:
  replSetName: rs0
```

```javascript
rs.initiate({ _id: 'rs0', members: [{ _id: 0, host: '127.0.0.1:27017' }] })
```

Keep `MONGODB_URI=mongodb://127.0.0.1:27017/booking_cinema`. Do not initialize again if the service already belongs to a replica set. This repository does not change or restart the installed MongoDB service automatically.

Run `npm test -w backend` for regression tests. For the complete transaction/concurrency suite, point `TEST_MONGODB_URI` to a test-capable replica set and run `npm run test:food-sales -w backend`. All tests create their own temporary databases and remove only those databases.

## UC-17.1–17.4: Manage Showtimes (Admin)
- RDS numbering: **UC-17.1 Add Showtime**, **UC-17.2 View Showtimes**, **UC-17.3 Update Showtime**, **UC-17.4 Delete Showtime**. The historical View/Add commit titles used reversed numbers; this correction retains shared Git history.
- Sign in at `/admin/login`, choose **Quản lý suất chiếu**, or open `/admin/showtimes`.
- View the paginated list and filter by movie. Add a showtime, edit it, or review its details and confirm deletion. Cancel leaves the data unchanged.
- Required fields: movie, cinema, room, future start time and a positive whole-number ticket price in VND. All form times use Vietnam time (UTC+7).
- Reuses Express, Mongoose, React and the Admin CSS; adds no packages. `CinemaRoom` holds `cinema`, `name`, `status` (`Active`, `Inactive`, `Maintenance`) and a unique, non-empty seat layout. Admin selects a configured room; the server verifies it independently. New showtimes copy that room's seats instead of a fixed 40-seat layout. An unbooked screening moved to another layout receives the selected room's layout; unchanged layouts keep their seat identifiers. Existing showtimes remain readable without the optional new `roomId` reference.
- Checks room conflicts across movies, including the movie duration plus a 15-minute cleaning buffer (BR-6). Deleted/C-classified movies, inactive/missing rooms, invalid layouts and screenings before the release date are rejected.
- Direct edit/delete is blocked for started screenings, seat holds, sold seats and any booking reference, including cancelled bookings, preserving transaction history (BR-12, BR-17). Controlled cancellation, customer notice and refunds are outside these four use cases.
- API: `GET /api/showtimes?movie=&page=1&limit=10`, `POST /api/showtimes`, `PUT /api/showtimes/:id`, `DELETE /api/showtimes/:id`. All require an active Admin session. Writes require JSON and validate the request origin.
- Admin-only `GET /api/showtimes/rooms` returns active configured rooms; `GET /api/showtimes/:id` retrieves the latest screening for conflict recovery without seat booking identifiers. On a 409 while editing/removing, the UI reloads the current data and asks Admin to review it before another confirmation; it never retries a write automatically.
- POST/PUT fields: `movie`, `cinema`, `room`, `startTime` (ISO timestamp with timezone), `price`. PUT/DELETE also require the `updatedAt` value from the list; stale data returns 409. DELETE sends `{ "updatedAt": "..." }` as JSON.
- Successful writes log the acting Admin and showtime ID to the server audit log. The existing public `/api/movies/showtimes` response remains unchanged and reflects saved changes.
- Room setup: copy `backend/rooms.example.json` to your own JSON file and enter the actual room names, statuses and seat numbers. Run `npm run import:rooms -w backend -- rooms.example.json` from the project root for the explicit demo example, or pass an absolute path to your own configuration. This setup command validates the input and only inserts missing rooms; it never overwrites rooms, layouts, showtimes or bookings. It is not run automatically. The UC-14 room/seat management UI remains a separate use case; this model and read endpoint provide the scheduling dependency.
- Schedule writes are protected against concurrency within the current single Node process; multiple backend instances would need a shared database lock. Audit logs need external retention for deployment. Do not change room names/layouts directly while the server handles scheduling; UC-14 must protect those changes under BR-17 when implemented. Existing ticket price snapshots are not changed by the setup command.
- Run `npm run test:showtimes -w backend` with MongoDB running. Tests create and remove a dedicated temporary database, leaving existing cinema data untouched. Run `npm run build` to verify the frontend build.
